- (decision) Source baseline from reviewed brief/addendum: Muvdash is a small Studio Ghibli movie browser, primarily a BMad learning project for its owner, with friends as secondary users. Success means completing BMad phases well enough to repeat them. Vue.js 3, Vite, TypeScript, Pinia, Vue Router; Home, Contact, About routes; Contact/About begin with simple page-identifying text and full content is deferred; Home GETs https://ghibliapi.vercel.app/films on mount, displays film cards (title, release_date, image, description, producer), client-side search across title/release_date/producer/director/description, detail modal with all available film fields and close action. Movie playback is out of scope. Final visual direction is deferred to the separate UX discussion. Long-term project can receive future features and maintenance.
- (decision) PRD discovery approach selected: Vision + Features (capability-first), per user choice.
- (decision) PRD coaching entry point selected: Vision + Features. External API constraint confirmed: use only the GET endpoint https://ghibliapi.vercel.app/films specified in the brief addendum; no other external APIs for now.
- (decision) Vision input: on entry, users see a dashboard with films fetched by GET from https://ghibliapi.vercel.app/films; a prominent client-side search filters by the already-confirmed fields; a mobile-first card list is planned, with visual design deferred to UX. Intended user outcome: find a film easily and quickly scan its information; users should feel helped and 'not alone' while using the app. Clarify what 'not alone' means before defining functionality.
- (question) User wants visual aids, tooltips, and extra information where needed to help users feel supported. Confirm whether 'not alone' means in-app guidance rather than social/community features; exact guidance placements/content can be defined during UX.
- (decision) Support intent confirmed: Muvdash should be simple and friendly, helping users with visual aids, tooltips, and extra information where needed. 'Not alone' means in-app help, not connecting users with other people; social/community features are out of scope for now. Exact guidance and visual treatment remain for UX.
- (decision) Vision confirmed by user: Muvdash is a simple, friendly Studio Ghibli film library and a practical project for learning the full BMad workflow. Friends should find and scan films quickly, with visual aids/tooltips/extra context where useful. It is not a streaming or social app.
- (decision) API failure behavior: show a friendly, funny error card with a retry action. User-proposed draft copy: 'Oops, seems like there are no movies today in the cinema. Please try again later. Until then, grab more popcorn'; final copy may be made funnier later.
- (decision) Empty API result behavior: when the GET request succeeds but returns an empty film list, show the same friendly error/empty card as API failure, including the retry action and draft copy.
- (decision) Search no-results behavior: when the loaded film list has no matches, show a separate friendly/funny message conveying 'No match for this search. Try with different texts'; exact copy can be refined later.
- (decision) Search matching is case-insensitive: capitalization differences such as 'Movie' versus 'movie' do not affect results.
- (decision) Search also supports partial matches within any configured field; e.g. 'ow' matches 'Howl'. Matching is case-insensitive.
- (decision) When the search query is cleared, restore the complete fetched film list.
- (override) Supersedes the earlier films-endpoint-only constraint: when necessary to display complete movie details, the app may GET related-resource endpoints referenced by film fields (such as people, species, locations, and vehicles) from the Studio Ghibli API. Fetch related data on demand as needed; do not display raw URLs in place of resolved data. Scope to these film-related Ghibli API resources; no unrelated external services are authorized.
- (decision) External data providers are limited to Studio Ghibli APIs only. Initial catalog fetch uses GET /films; related Ghibli endpoints referenced by film records may be called as needed to present complete details. No other providers are in scope.
- (decision) Initial film-list loading state: display skeleton movie cards. Exact skeleton appearance and motion are deferred to the UX discussion.
- (decision) Related-detail API failure behavior: show an error modal instead of the movie details, with friendly draft copy such as 'Oops, the details are not available now. Try again later'; final wording may change. Retry-action behavior for this modal remains to be confirmed.
- (decision) Modal behavior: every modal has an X close button. If a related-details request fails, show only the friendly error message and X close button; do not show movie details or a retry action in that error modal.
- (event) Coaching discovery for Vision + Features is complete for now; user has no additional feature details at this point. Draft PRD from confirmed decisions and preserve deferred UX/copy questions without assumptions.
- (question) Provider-boundary clarification: the example record in _bmad-output/api_structure.md returns image and movie_banner URLs hosted at image.tmdb.org. Confirm whether 'Ghibli APIs only' prohibits only other data APIs, or also prohibits loading image assets from non-Ghibli hosts.
- (override) Clarifies and supersedes the prior 'Studio Ghibli APIs only/no other providers' host restriction: the app may load or request any URLs supplied by the Ghibli API response contract, including related-resource URLs and external image asset URLs such as image.tmdb.org, so associated data and assets display correctly. This permission is limited to URLs present in Ghibli film/API data; do not add independent, unrelated providers or endpoints.
